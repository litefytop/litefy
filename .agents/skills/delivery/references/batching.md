# 攒批判定与纪律

1. 适用范围：只收**同步型**工作——同一内容存在多份副本、且内容仍会再改的场景（典型：双语文档，zh 正本改完、en 发布前同步）。担心的是「内容再改导致同步多次」；不存在二次同步的一次性修复不进攒批
2. 一次性修复（当场修）：唯一正本上的问题，改完即终结——旧词表迁移、死代码清理、bug、文档与实现脱钩
3. 判据：修复产物有几份、之后会不会再改导致重复同步？会 → 攒批；不会 → 当场修。判定只做一次，修/攒不摇摆
4. 已落盘的修改不回退：回退是二次浪费；攒批件的内容问题留到发布批修正
5. 双语同步是唯一攒批场景：机制、白名单登记与发布前补齐一律见 i18n-gate.md，本文件不重复
6. 台账去处：攒批欠账归各自登记处（双语归 sync.json，见 i18n-gate.md）；一次性工作不留台账，修完即完
7. 用户明确指令当场修 → 只修指名那件，不顺手扩圈
