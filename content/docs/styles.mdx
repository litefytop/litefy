Litefy components ship unstyled. A **style** is a self-contained package: you pick one at install time and it owns every color, radius, shadow, motion and typography rule in your app. A route loads exactly one style's stylesheet — there is no runtime switch, and styles never mix within a page. The pane below lists that one file per style: click it to read the token ladder, the palette ramps and the `@theme` mapping the style is built out of.

<StyleStylesheets />

Every style package carries exactly one stylesheet (`index.css`: tokens, the `@layer base` block, the `@theme` mapping — a namespace only for a dimension solved back out of another constant (`--height-*` / `--width-*` / `--size-*` / `--padding-tight|snug|loose` / `--transition-duration-*`), which is where `h-control`, `py-snug` and `duration-sm` come from; whitespace has no names and uses the numeric spacing scale — plus its `@custom-variant` roles and `@utility` primitives; no per-component file), a light + dark color scheme (the `.dark` class on `<html>` flips it), and a `design.md` design-language file (preview/download online; not installed with the stylesheet).

- **Install it**: commands and options are on the [Installation](/en/docs/installation) page.
- **Read its design language**: each style has one `design.md` (the skin-specific design language file, aimed at AI design tools and coding assistants) — preview or download it below.

- **See it painted**: [Litefy's home page](/) carries one card per style that opens that style's gallery, and the demos on any component page render under the stylesheet loaded by the current route — switching styles means switching routes.

## Sizing and spacing

Every dimension is a multiple of the same spacing base value `--spacing` (minimal, neon-gradient and clinical answer 0.25rem = 4px, neo-brutalist answers 0.375rem = 6px) — `w-112`, `p-4` and `gap-3` are multiples, not pixels. Switching styles rescales the whole library in step, so skins write no fixed rem / px values. Control geometry uses multiples of 11: `w-11` is the touch target (44px on the default schemes), and the compact tier multiplies the base value by 0.75 then rounds down to whole pixels (3px / 4px), shrinking `w-11` to 33px (44px on neo-brutalist). The compact tier takes effect automatically — a coarse primary pointer (touch screens; phones and tablets sit on the same tier in both orientations) or a viewport narrower than 48rem (narrow desktop windows and emulated debugging share the tier) enters compact; only a fine pointer with a viewport at least 48rem wide gets the comfortable tier, so desktop always sits at the 44px base with nothing to configure.

Spacing follows one decidable hierarchy: **the padding inside a group must be smaller than the gap between that group and everything outside it**, with at least one tier of difference (4 units). `gap-2` inside a group and `mt-6` between groups reads as grouping; when the two are equal it reads as nothing — merely writing "a multiple of 4" is not a constraint.

## Width lanes

Width is not decided component by component. Ask six questions in order and stop at the first hit; never mix two lanes on the same element.

1. **Is it continuous reading text?** Put `max-w-[40em]` on it. This is the only lane that uses em — it must follow the font size rather than the grid: 40 Chinese characters and 80 Latin characters per line hold at the same time (WCAG 1.4.8). This site's body column takes this lane.
2. **Is the width decided by the parent cell?** Inputs, password fields, textareas, the select and multi-select triggers and the number input root all ship a default intrinsic width of `w-55` (220px: derived by giving the prefix and suffix one `w-11` cell each, which still leaves 3 cells for the value area in the worst case); in form layouts the consumer takes over with `w-full`, and narrow containers tighten it automatically.
3. **Is the content a fixed-length countable number?** Number widgets use static multiples of 11: the stepper's value area is always `w-11` (one cell — overflowing content scrolls horizontally inside the box, zero runtime calculation), and the total width is nominally 3 cells (one each for the two step buttons and the value area); widen the value area yourself when you raise `max`. Each end of a range input takes `min-w-11` and stretches with the cell.
4. **Does it compete for leftover space with siblings on the same axis?** Stretchy widgets such as slider tracks, progress bars and chart canvases write `w-112 grow min-w-0 max-w-112` on the body and `min-w-[min(100%,--spacing(32))]` on the control root: when space runs short they shrink all the way and never squeeze a sibling out. The floor goes on the root only — on the body the percentage is computed against the whole container, which cannot see the space siblings have taken.
5. **Is it a floating layer out of the document flow?** Its width answers to the viewport, not to the parent cell. Centered widgets (Dialog) write `max-w-[min(100%_-_--spacing(8),--spacing(112))]`, leaving an 8-unit gutter on each side and yielding automatically on narrow viewports; edge-attached widgets (Drawer) write their fixed tier on the main axis into `--litefy-pane-size`, then cap it with `max-w-full` / `max-h-full`.
6. **None of the above?** Pick from the tier table by role. Tiers sit on two bases: control-level small containers always take **multiples of 11** (number widget value areas, page-number inputs, inline small buttons — `w-11` is the 44px touch base); container-level ones always take **multiples of 16**: on the default schemes 16 units = 4rem, so for 24rem write `w-96`, and when you switch schemes the whole tier scales with the base value — no recalculation.

The tier table (in units):

- `11` the minimum cell for number widget value areas and inline small buttons
- `32` the floor root for stretchy widgets
- `48` dropdown-menu family panels and the floor for top/bottom drawers
- `64` the floor for left/right drawers
- `80` inline narrow selects and `size="sm"` drawers
- `96` the drawer default tier
- `112` the Dialog default tier, the toast viewport and the stretchy track ceiling
- `128` wide Dialogs (forms, two-column content) and `size="lg"` drawers

Arbitrary values cannot contain spaces: write `_` in the gaps of `calc` and `min()` (the class scanner splits on whitespace, and a string containing spaces silently generates no CSS).
